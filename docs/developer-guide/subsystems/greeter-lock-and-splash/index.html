Greeter, lock and splash

argvus-greeter provides the greetd interface. The session-loading spinner is the Wayland mode of the handoff helper (/usr/lib/argvus/greeter/handoff --wayland), started by argvus-session-loading.service; the GTK overlay argvus loading-theme covers theme transitions and direct reloads. argvus-boot-splash provides the separate boot splash. argvus-lock provides Hyprlock configuration.

Theme state is handed across the greeter and session transition, but these packages have different lifecycles and installed payloads.

The greeter runs before the user’s authenticated session and uses greetd’s IPC/PAM boundary. The session-loading overlay starts when the new Wayland socket becomes available and ends once argvus sessionctl ready has started the desktop components, so it covers the whole session startup. The Plymouth theme belongs to the boot path and is not the login screen. The lock component is used after login and does not replace either greeter.

The login handoff has a DRM surface of its own. Once authentication succeeds, the greeter starts /usr/lib/argvus/greeter/handoff (argvus-greeter-handoff) before it asks greetd to start the session. The helper takes DRM master as soon as the greeter compositor releases it and keeps a frame on screen until the user compositor takes over. It keeps running after the greeter exits. As soon as greetd accepts the session, the greeter ends its compositor: greetd starts the user session only after the greeter session ends, and the compositor does not leave on greetd’s SIGTERM, so without this the login waited for greetd’s 5-second kill. An active Hyprland turns every output off when it exits, and the monitor then loses its signal. So before ending its compositor, the greeter switches the seat to the empty VT 12 (logind Seat.SwitchTo, which polkit allows an active session; VT 12 is above the autovt range, so no getty starts there). It addresses the seat from XDG_SEAT (seat0 when unset), not as seat/self: Kitty moves the greeter into a systemd scope of its own, outside the logind session, where logind cannot resolve the caller’s seat. logind deactivates the greeter session and takes DRM master from its compositor, which keeps running with its last frame on screen. The helper takes master, replaces that frame with a page flip and hides the greeter’s cursor. The greeter waits for it (the helper answers ping only once it draws) and only then ends the compositor. It stops only the start-hyprland watchdog, the greeter session command, with SIGKILL (greeter.watchdog-stop-requested in the timing log): greetd then starts the user session at once, and a stopped watchdog cannot relaunch Hyprland. The compositor, inactive and without DRM master, is asked to exit later (greeter.compositor-exit-deferred): a process of its own group waits until the handoff surface removes its socket, at most 10 seconds, then 3 more seconds, and runs argvus config hyprland exit. The compositor’s teardown hands its devices back to logind, and on the NVIDIA driver logind then spends about half a second closing the DRM client, answering nothing else, the user session’s CreateSession included; that happens whether the compositor exits or is killed, so the exit is moved out of the login. Under greetd, though, the compositor is in the foreground process group of the greeter’s terminal, and greetd’s session worker controls that terminal: when the worker exits after the watchdog, the terminal hangup ends the compositor at once (compositor-in-foreground=true in the mark), its close still runs during the login, and the deferred request finds no compositor. Keeping the compositor past the login would need it in a session of its own. The watchdog’s PID is the parent of the compositor named by the instance’s hyprland.lock, and both are checked to be the expected programs of the greeter user. The mark also records whether the watchdog is a controlling process and whether the compositor is in the terminal’s foreground group, because a controlling process that exits hangs up that group. Without a watchdog, the greeter asks the compositor to exit at once (greeter.compositor-exit-requested). An inactive compositor leaves the outputs alone when it exits, and the framebuffers the kernel removes when it closes its device are no longer on screen. greetd switches back to its VT for the user session. When the switch or the wait fails, the greeter writes greeter.handoff-takeover-failed error=<reason> to the timing log (its own log is in its runtime directory, which logind removes at logout) and asks the compositor to exit anyway, and the output goes dark for a moment while the monitor syncs again at the helper’s modeset. On a system where fbcon is bound to the VTs, the console can show for an instant at the VT switch. Before it waits, the helper finds the output and paints its first frame through an observer descriptor (handoff.prepared), since neither needs DRM master, so the frame goes on screen as soon as master is free. It tries a page flip only when the primary plane still holds a frame; with an empty plane the kernel refuses the flip, and the helper sets the CRTC with the same mode instead. While it waits for DRM master, the helper keeps a descriptor open on each card, so the compositor’s exit is never the last close that makes the kernel restore the fbdev mode, and it logs every CRTC change as handoff.crtc in the timing log (a fb=0 or mode_valid=false line means the output went off between the two masters). It reads the connectors from their cached state, without probing them again, and logs handoff.page-flip-failed errno=<n> when the page flip is refused and it falls back to a modeset. greeter-session disables core dumps for that compositor (ulimit -c 0), so a crash during its teardown does not keep the display off while the core is written. The greeter compositor runs without Xwayland: Kitty and the handoff surfaces are Wayland clients.

The greeter splash, this surface and the session spinner read as a single splash. The greeter splash and the session spinner are the same helper in Wayland mode: a plain shared-memory layer-shell client that shows its first frame a few milliseconds after it connects (the GTK overlay needed about 300 ms, while the compositor already showed its background), with no GTK in the login path. All three draw the same spinner from argvus-loading-theme-core: four squares that grow, travel to the next corner and shrink back in a 1.5 s cycle (the CSS loader keyframes, with cubic-bezier(0.3, 1, 0, 1) on each segment), the same size in physical pixels, the user accent as color (the greeter passes --accent to both helpers), with the frame taken from CLOCK_MONOTONIC so the animation does not restart when one process takes over from another. When the greeter compositor left the output on in the same mode, the surface shows its first frame with a page flip instead of a modeset, so the monitor does not resynchronise. Hyprland’s first modeset scans out a buffer it has not drawn into yet (black), and its first frame comes 150–210 ms later, once its event loop runs. So on release, while it still holds DRM master, the surface also puts a copy of its frame on a free overlay plane of the CRTC (handoff.overlay plane=<id>). Hyprland only drives the primary and cursor planes, so the overlay stays above its first frames, with the spinner still animating in the overlay buffer (writing to it needs no DRM master). The session spinner runs with --retire-handoff: once its first frame is on every output it sends retire, and the surface removes the overlay framebuffer, which turns off that plane alone (handoff.retired). If no retire arrives within 3 seconds after Hyprland replaced the primary plane, the surface removes the overlay itself (handoff.retire-timeout), and after 10 seconds without a replacement it gives up (handoff.replacement-timeout). Without a free XRGB8888 overlay plane (handoff.overlay-unavailable), the surface keeps only its primary buffer, with the spinner animating, until Hyprland replaces it, and Hyprland’s undrawn first buffer shows for that moment. Hyprland maps the argvus-loading-theme layer without an animation (no_anim layer rule), so the spinner appears and leaves in a single frame. Until it maps, Hyprland paints the splash background of the active theme, which argvus config project writes as background_color in the generated hypr/state.lua.

argvus-start sends release to its socket (/run/argvus-greeter/handoff.sock) just before it launches Hyprland, and the helper acknowledges only after it has dropped DRM master. A session without a greeter sends the same command and finds no surface, so nothing happens. A failure to start the surface is logged and does not stop the login. While it runs, send it commands with /usr/lib/argvus/greeter/handoff --send theme=<name>, --send ping (answered once it draws), --send release or --send retire. The socket stays open until the surface exits. The socket and the greeter’s pre-login session.log live in /run/argvus-greeter, which systemd-tmpfiles creates owned by the greeter user with mode 0755: only the greeter writes there, and the session that logs in only reads the log and connects to the socket.

This separation matters when diagnosing a visual problem: a missing boot splash is a Plymouth/package issue, a blank transition is a session-loading or compositor-readiness issue, and an authentication failure belongs to greetd/PAM rather than the desktop session.

A theme switch shows no overlay: the running desktop changes in place. A direct session reload passes the selected theme explicitly to /usr/lib/argvus/loading-theme/splash. A direct reload (argvus sessionctl reload, SUPER + Shift + R) shows the session splash only when it recreates a surface: a restart of a Waybar bar or of the Control Panel, or the fallback full plan. The projection runs without it, and changes that reload in place (Hyprland, theme consumers, wallpaper, Dunst, polkit, hypridle) never show it; see the reload targets in argvus-config. The Control Center holds the same splash itself (argvus config transition-overlay hold) for an Apply that restarts a bar or the panel, so the reload it triggers starts no second one. It uses the spinner-only mode, so its first mapped frame is opaque, and it is started with --detached: the splash outlives the short-lived argvus config session-splash start helper that spawns it, because a parent-death signal would stop it as soon as that helper exits. The reload stops the splash after the runtime half finishes, on every exit path. The splash palette is only a fallback. Verify the installed binary and package payload when source changes are not visible in the running session.
