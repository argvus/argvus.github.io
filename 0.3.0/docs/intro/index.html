ARGVUS Desktop Environment

Section titled “ARGVUS Desktop Environment”

ARGVUS is a complete, ready-to-use desktop environment built around Hyprland and packaged natively for Arch Linux.

ARGVUS is not a Linux distribution, a Hyprland configuration repository, or a collection of personal dotfiles. It is an integrated desktop environment that owns the graphical user session, manages the lifecycle of its essential desktop components, defines the desktop experience, provides native desktop infrastructure, and integrates selected upstream applications where developing an ARGVUS-specific replacement would provide little benefit.

Hyprland is the Wayland compositor used by ARGVUS. Arch Linux is the operating-system platform on which ARGVUS is currently packaged and supported.

In simplified form:

The distinction is intentional:

Arch Linux provides the operating system. ARGVUS provides the desktop environment. Hyprland provides the compositor.

Why ARGVUS is a desktop environment

Section titled “Why ARGVUS is a desktop environment”

There is no requirement that a desktop environment must develop every application that runs inside it.

Projects such as GNOME and KDE are more than desktop environments: over time they have also developed large application ecosystems, frameworks, libraries, utilities and developer platforms. Applications such as file managers, terminals, text editors, image viewers and document readers strengthen those ecosystems, but owning replacements for every application category is not what fundamentally defines a desktop environment.

A desktop environment is primarily responsible for the graphical user session and for presenting an integrated environment in which applications run.

That includes responsibilities such as:

  • establishing and identifying the graphical desktop session;
  • starting and stopping the desktop session;
  • managing the lifecycle of essential desktop processes;
  • defining the desktop shell and its interaction model;
  • providing panels, launchers, menus and system surfaces;
  • managing appearance and desktop-wide configuration;
  • integrating authentication, accounts, storage and session actions;
  • exposing coherent defaults and application associations;
  • integrating system services needed by the graphical environment;
  • providing a consistent configuration and theming model;
  • supervising desktop services and recovering them when appropriate;
  • ensuring that session-owned processes are cleaned up on logout.

ARGVUS performs those responsibilities as an integrated project.

This is different from installing Hyprland and adding a few unrelated configuration files.

ARGVUS is not just Hyprland

Section titled “ARGVUS is not just Hyprland”

Hyprland is a Wayland compositor. It is an important part of ARGVUS, but it is not the whole desktop.

ARGVUS builds and manages a desktop around it.

Conceptually:

The compositor manages windows, outputs, workspaces and Wayland composition.

ARGVUS owns the broader environment around it: session lifecycle, configuration, desktop services, shell components, process supervision, appearance, integration and user-facing behavior.

Replacing Hyprland would be an architectural change to ARGVUS, but using Hyprland does not make ARGVUS merely a Hyprland configuration.

Session supervision

Section titled “Session supervision”

ARGVUS uses systemd --user as the process supervisor for persistent components that belong to the desktop session.

Conceptually:

This provides:

  • explicit process ownership;
  • dependency and startup ordering;
  • restart policies;
  • centralized logging through the journal;
  • clean session shutdown;
  • protection against accidental duplicate processes;
  • separation between ARGVUS-owned services and unrelated user processes.

The session manager does not need to reinvent those facilities inside a custom monolithic daemon. ARGVUS defines the session architecture while systemd --user provides the underlying supervision mechanism.

The ARGVUS session target

Section titled “The ARGVUS session target”

The running desktop is represented by an ARGVUS-specific user target.

Conceptually:

The target represents the lifetime of the ARGVUS graphical session.

Components that belong to the session are tied to this lifecycle rather than being globally enabled for every desktop environment the user may run.

As a result, logging into GNOME, KDE Plasma, plain Hyprland, Sway or another environment does not automatically start ARGVUS-specific desktop services.

Environment management

Section titled “Environment management”

The session manager establishes the environment used by ARGVUS and propagates it to the user service manager and D-Bus activation environment where necessary.

This includes the desktop’s XDG configuration hierarchy and ARGVUS-specific runtime paths.

ARGVUS packages do not need to copy their complete configuration into the user’s home directory.

The configuration model remains:

For applications that support XDG system configuration, /usr/share/argvus participates in the configuration search hierarchy while normal system configuration such as /etc/xdg remains available.

This makes configuration discovery part of the session architecture rather than a collection of dotfiles copied once into $HOME.

Hyprland startup and readiness

Section titled “Hyprland startup and readiness”

Hyprland remains the compositor of the ARGVUS Desktop Environment.

The session manager is responsible for launching it with the supported ARGVUS environment and configuration rules.

ARGVUS preserves:

  • user Hyprland overrides;
  • packaged fallback configuration;
  • configuration validation;
  • virtual-machine detection and workarounds;
  • correct graphical-session environment;
  • display-manager support;
  • TTY session support.

Once the compositor is ready, the ARGVUS desktop target is started and the supervised desktop services become active.

Conceptually:

Hyprland is therefore the compositor inside the session, not the owner of the desktop process lifecycle.

Reloading the desktop

Section titled “Reloading the desktop”

Desktop reloads are also handled as session operations rather than by indiscriminately killing processes.

A reload can re-apply mutable configuration and selectively reload or restart only the components that require it.

Conceptually:

This preserves the user’s graphical session while keeping process ownership under the session manager.

TTY session support

Section titled “TTY session support”

argvus-tty allows the same ARGVUS Desktop Environment to be started without a graphical display manager.

That path performs the additional integration needed when entering the graphical environment from a TTY and ultimately launches the same ARGVUS session lifecycle.

Conceptually:

ARGVUS is therefore not tied to one specific display manager.

A desktop environment does not need its own file manager or terminal

Section titled “A desktop environment does not need its own file manager or terminal”

ARGVUS intentionally uses upstream applications for some general-purpose tasks.

A file manager, terminal emulator, browser, text editor, media player or image viewer is an application that runs inside the desktop environment.

Such applications can be developed by the same project as the desktop, but they do not have to be.

This separation allows the project to concentrate development effort on components that define the desktop experience while integrating mature upstream software for generic application roles.

The project therefore follows a practical principle:

ARGVUS develops the components that define the ARGVUS desktop experience and integrates high-quality upstream applications where reinventing them would not meaningfully improve the desktop.

Developing an argvus-files, argvus-terminal or broader application suite in the future is possible, but those applications would expand the ARGVUS ecosystem. They are not a prerequisite for ARGVUS to be a desktop environment.

ARGVUS versus dotfiles or a “rice”

Section titled “ARGVUS versus dotfiles or a “rice””

A set of Hyprland dotfiles generally configures an already existing compositor and a collection of applications.

Conceptually:

ARGVUS has a different architecture:

The important distinction is ownership.

With ordinary dotfiles, the user owns a configured collection of independent programs.

With ARGVUS, the project defines a supported desktop session, packages its components, establishes configuration precedence, supervises essential processes and publishes those components as one coordinated environment.

That is why ARGVUS is more accurately described as a desktop environment than as a rice or dotfiles project.

ARGVUS versus a Linux distribution

Section titled “ARGVUS versus a Linux distribution”

ARGVUS is also not a Linux distribution.

A useful distinction is:

A desktop environment controls the graphical user experience and user session. A Linux distribution controls the operating-system platform and its lifecycle.

ARGVUS starts from an existing Arch Linux installation.

Arch remains responsible for the operating-system base, including core system packages and the normal system update model.

ARGVUS is then installed as the desktop environment.

ARGVUS does not define itself through its own operating-system installer, base-system fork, kernel policy, bootloader policy or independent operating-system lifecycle.

Those are distribution-level responsibilities.

The project intentionally leaves those responsibilities to Arch Linux.

The ARGVUS package repository does not make ARGVUS a distribution

Section titled “The ARGVUS package repository does not make ARGVUS a distribution”

ARGVUS publishes signed Arch packages through its own package repository.

That repository exists to distribute ARGVUS components and selected packages needed by the environment.

Having a package repository does not by itself create a Linux distribution.

An Arch package can depend on packages from the official Arch repositories. pacman resolves those dependencies across configured repositories.

Conceptually:

The preferred packaging rule is:

If a suitable package already exists in the official Arch repositories and ARGVUS does not need to modify it, ARGVUS should depend on that package instead of republishing it.

The ARGVUS repository should primarily contain software owned by ARGVUS, packages requiring ARGVUS-specific changes, and selected third-party software that cannot reasonably be obtained from the supported Arch repositories.

This keeps the responsibility boundary clear:

Responsibility boundary

Section titled “Responsibility boundary”

The intended architecture of the project can be summarized as follows:

Layer Primary responsibility
Linux Kernel and low-level operating-system foundation
Arch Linux Operating system, package base and system lifecycle
Wayland Display protocol
Hyprland Wayland compositor and window/workspace management
ARGVUS Desktop session lifecycle, process supervision, desktop experience, integration and desktop services
Applications User workloads running inside the ARGVUS desktop

ARGVUS should therefore focus on desktop responsibilities rather than duplicating distribution responsibilities.

Native components and integrated components

Section titled “Native components and integrated components”

ARGVUS is split into focused packages and repositories rather than one monolithic package.

Current project components include:

  • argvus — the main desktop configuration and integration layer;
  • argvus-session — ARGVUS session lifecycle, environment and process-supervision infrastructure;
  • argvus-appearance — shared appearance resources such as wallpapers and fonts;
  • argvus-storage — removable-storage integration;
  • argvus-calendar — native calendar integration;
  • argvus-default-apps — default-application management;
  • argvus-accounts — local account metadata and avatar integration;
  • argvus-greeter — GTK4 login greeter for greetd;
  • argvus-waybar — ARGVUS Waybar integration and packaging;
  • argvus-splash — ARGVUS Plymouth boot experience;
  • argvus-extras — selected additional packages used by the environment.

ARGVUS also integrates upstream projects such as:

  • Hyprland;
  • Waybar;
  • Rofi;
  • Wofi;
  • Quickshell;
  • terminal emulators, file managers and other general-purpose applications.

An integrated upstream component does not become ARGVUS-developed software.

ARGVUS preserves that distinction in its documentation and attribution.

What ARGVUS owns is the desktop environment in which those components are selected, configured, started, supervised and integrated.

Project focus

Section titled “Project focus”

ARGVUS is intentionally focused as a desktop environment for Arch Linux.

The project does not need to become a Linux distribution in order to provide a complete installation experience on Arch, and it does not need to create replacements for every desktop application in order to qualify as a desktop environment.

Its development priority is the layer that differentiates the ARGVUS experience:

General-purpose applications can continue to come from upstream projects unless an ARGVUS-specific application has a clear reason to exist.

This keeps the project maintainable and gives it a clear identity.

Definition

Section titled “Definition”

The preferred project description is:

ARGVUS is a complete Hyprland-based desktop environment for Arch Linux.

A more architectural description is:

ARGVUS is a desktop environment that owns and manages the graphical session, uses Hyprland as its Wayland compositor, supervises its essential desktop components through the ARGVUS Session Manager, integrates native ARGVUS services and selected upstream applications, and is packaged natively for Arch Linux.

The first sentence is suitable for project pages and short descriptions.

The second explains the technical boundary precisely.

Development status

Section titled “Development status”

ARGVUS is under active development.

The project provides a distinct Wayland desktop session, a dedicated session-management layer and a growing set of coordinated ARGVUS components.

The architecture is intentionally modular: ARGVUS owns the session and desktop experience while continuing to reuse mature upstream software where appropriate.

That development model does not make ARGVUS a distribution or a collection of dotfiles.

ARGVUS is developed as a desktop environment.
